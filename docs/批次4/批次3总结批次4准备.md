## ✅ 批次4最终技术方案（定版）

本方案整合批次3评估与遗留项，补齐灰度启用、回滚、治理与测试等缺口，作为批次4实施与验收的唯一依据。

### 一、范围与目标
- 从“双路径+功能开关”的保守形态，收敛为“BLoC 单源驱动”的唯一路径
- 清理遗留代码与旁路依赖，收敛 UI 状态为 GoalState 单源
- 建立可持续的治理与回归保护体系（CI/PR 模板/测试）

### 二、阶段A：灰度启用与固化单路径（1–2周）
1) 开关启用顺序与灰度策略
- 顺序：dataLoadingViaBloc → goalCRUDWriteThrough → uiStateWriteThrough
- 灰度：支持按用户群/比例/配置渐进启用；每步至少观测2–3天
2) 关键指标与监控
- 事件耗时：GoalBloc 事件处理P95≤80ms；最大≤150ms
- UI 侧：关键交互≤100ms；重建次数不异常（相对基线±20%以内）
- 稳定性：GoalError 率不升高；崩溃/异常告警无回归
- 数据侧：DB查询P95稳定；重载次数不异常
3) 快速回滚机制
- 任一指标超阈值：自动/手动切回上一步开关状态
- 所有开关可一键回滚（flight config），并记录回滚原因
4) 固化为默认与删除旧路
- 连续N天（建议≥3）指标稳定→默认开启该开关，并锁定
- 完成三步后，进入阶段B删除旧路径

### 三、阶段B：清理与治理定型（1–2周）
1) 代码清理
- 删除：syncStateFromBloc、_batchStateUpdate/_pendingStateUpdates、本地影子态（_isLoading/_error 等）
- 移除：UI 中所有 DatabaseHelper 旁路（含“受保护分支”）
- 清理：未使用导入/方法、print 调试、use_build_context_synchronously、deprecated API（按表替换）
2) UIBatchUpdater 决策
- 出台使用规范（场景、优先级、反模式），基准对比 Equatable+buildWhen 的收益
- 做出“保留/优化/淘汰”决策并执行
3) 持久化策略拍板
- UI 偏好（显示选项/视图模式）统一采用 HydratedBloc 或 settingsRepository（默认建议 HydratedBloc）
- 若使用 settingsRepository，补充仓库接口与读写点，避免 UI 直接持久化
4) 目标树一致性校验
- 明确哪些操作需要触发 RefreshGoalTree（如父子关系/批量变更）
- 覆盖测试：状态切换/批量更新后父子一致性
5) 资源与内存
- 审计 StreamSubscription 生命周期（GoalPage/Timeline 等）
- 图片与缓存释放策略检查，防止内存膨胀
6) 国际化与错误信息
- 统一错误来源与映射（Bloc→UI），支持本地化占位与友好提示

### 四、测试与度量（覆盖/性能/体验）
- 集成测试：视图切换、目标选择、CRUD、显示选项、加载/错误（页面级）
- 性能测试：关键事件与UI更新≤100ms；基线对比报告输出
- 一致性测试：单源状态（无 UI 本地回灌/旁路）与目标树一致性
- 覆盖门槛：核心流程≥80% 行覆盖；关键事件分支100% 覆盖

### 五、CI/PR 治理落地
- 将 architecture_guard_rules.md 接入 CI：
  - UI 禁止直接 DatabaseHelper/Repository 调用
  - UI 禁止对 BLoC 管理字段 setState 回灌
  - 关键 handlers 的 emit 策略注释与响应时间目标
  - 自动运行验证/回归脚本（verify_phaseX/performance_*）
- PR 模板 Checklist（强制项）：
  - [ ] 无 UI→DB 旁路与本地回灌
  - [ ] 新代码通过 Bloc 驱动测试与性能校验
  - [ ] CI 架构守护全部通过

### 六、风险与缓解
- 指标回归：保留一键回滚与自动阈值告警
- 大规模删除回归：小步提交，阶段性全量验证
- 业务一致性：明确 RefreshGoalTree 触发条件并加测
- 长期开关腐化：阶段B末尾清理不再需要的开关与分支

- CI 架构守护“必跑必过”；集成与性能测试通过；关键交互≤100ms
文档层
- 迁移指引与模板完成；UIBatchUpdater 决议/规范有据可循；PR 模板生效
治理层
- 开关默认开启并清理冗余；新页面可按模板复制成功经验
