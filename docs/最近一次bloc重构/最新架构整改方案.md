## 迁移策略与阶段

### 阶段0：立即止血与稳定化（先修复当前失效功能）

目标：恢复以下 5 类核心功能在现有混合架构下均可用
- 目标编辑（增/改/删）
- 日期设置（目标日期/截止）
- 显示选项控制（标题/描述等）
- 视图切换（全屏/时间线/网格）
- 目标状态管理（完成/进行中/暂停）

策略：
- 不动 BLoC 结构，先在现有 GoalPage 中补齐“影子模式”和“同步”的缺口，确保 UI → DB → UI 流转与 UI → BLoC → 状态 → UI 的一致
- 统一入口：对每个操作，在 UI 调用后，立即发相应 BLoC 事件用于同步（现有代码多处已这样做，但存在遗漏/竞态）
- 关键校验点：
  - 增删改后，currentGoal 与 goals/allGoals 必须一致更新（本地与 BLoC 同步）
  - 视图切换与显示选项：UI setState 与 BLoC ToggleXXX 事件二者都发生，避免 BLoC 未处理时 UI 无反馈
  - 日期设置：更新 DB 后触发 UpdateGoalDate（或 UpdateGoalWithValidation）事件，验证 listener 中 currentGoal 与 goals 列表更新
- 输出：提交“修复补丁”保证现有混合模式下五类功能恢复，作为迁移前的稳定基线

风险控制：
- 仅在 GoalPage 局部改动；不修改 GoalBloc 的行为逻辑
- 按功能分支核对 setState_detailed_inventory.md 中的对应点逐项打勾

验收：
- 手工核验 + 现有测试运行（test/bloc、test/integration 等），新增针对五功能的最小端到端测试

---

### 阶段1：只读改造（UI 渲染由 BLoC 驱动，写操作暂保留原路径）

目标：将 GoalPage 的 UI 渲染改为“仅根据 GoalBloc 状态展示”，减少 setState 的“源记录”职责；但写操作仍沿用现有 UI→DB→BLoC 影子同步路径，降低风险

做法：
- 将 appBar、菜单、主体区域改为：
  - 使用 BlocBuilder<GoalBloc, GoalState> 渲染
  - 使用 buildWhen 精细控制重建（视图模式、当前目标、显示选项、加载/错误）
- 保留现有“操作后发事件”的同步，确保 UI 在 BLoC 状态未更新时也能即时响应；完成后逐步关闭 UI setState 的“源状态更新”，只保留必要的局部 UI 临时态（如对话框内部）

风险与缓解：
- 双源仍存在，但 UI 以 BLoC 为准；若出现不一致，以 BLoC 渲染结果为权威
- 保留影子模式适配器，作为诊断辅助（性能/状态对账）

验收：
- 运行现有与新增测试，保证五类核心功能在“BLoC 驱动的渲染”下无回退

---

### 阶段2：写路径切换（数据写操作从 UI/DB 迁到 BLoC/Repository）

目标：让所有“写操作”（增/改/删/设置日期/状态切换/显示选项/视图模式）通过 BLoC 事件落地，DB 仅在 Repository 中被调用。UI 不直接触碰 DB。

做法（渐进式、按功能分批切换）：
- 批次1：显示选项/视图切换（无数据存储/弱数据一致性要求）
  - 从 UI 层移除 setState 更新，统一改为发事件 + 纯 BLoC 渲染
- 批次2：目标选择/编辑态（无 DB 变更或弱变更）
- 批次3：日期/状态/目标编辑（增删改）（涉及 DB）
  - 移除 UI 直接调用 DatabaseHelper 的路径
  - 仅发对应 BLoC 事件（UpdateGoalWithValidation、UpdateGoalDate、AddGoalWithDetails、DeleteGoalWithCleanup 等）
  - 在 GoalBloc 完成 DB 操作后 emit 新状态（GoalsLoaded），UI 随之重绘
- 每批切换后运行回归测试与手工验收；若异常，feature toggle 回退到“上一批次”状态

风险与缓解：
- 写路径切换最敏感，逐批次切换，先简单后复杂
- 每个事件补充单测（mock repository），同时做最少量 UI 集成测试

---

### 阶段3：收尾清理（去除影子模式与同步 setState）

目标：移除 GoalPageBlocAdapter、syncStateFromBloc、批处理 setState 等过渡性代码，收敛为“纯 BLoC 单源”

做法：
- 删除影子模式适配器调用与注入
- 删除 setState 同步代码、_batchStateUpdate 等逻辑
- Dialog/临时态保留最小 setState（StatefulBuilder 范畴）

验收：
- 全量测试通过；手工场景回归；检查 setState 清单收敛

## 风险评估

高风险点
- 双源到单源切换（尤其写路径）
- currentGoal 与 goals/allGoals 不一致导致 UI 难以定位的错误
- 批处理 UI 更新机制与 BlocBuilder 重建策略的相互影响

缓解策略
- 渐进式迁移、分批交付与随时回滚
- 在每个批次的关键事件/状态处增加单测
- 使用 buildWhen 减少无关重建，避免“看起来失效”的假象
- 日志与性能监控保留到收尾阶段，便于定位问题

## 是否先修复再迁移？

是。当前你报告“核心功能都无法正常工作”，必须先在现有混合架构下“修复与稳定”，形成可对比的“稳定基线”，再做迁移。否则迁移过程中很难分辨是迁移导致的回退还是遗留缺陷。

## 复杂状态与交互的处理方法

- 状态单源：最终以 GoalState 为唯一“真源”，UI 不存 copy，避免 listener 中 setState 回灌
- 细粒度状态：GoalsLoaded 维持现有细分字段，但合理使用 copyWith 与 Equatable，配合 buildWhen 避免整页重建
- 交互路径统一：所有写操作发事件；Repository 负责 DB；Bloc 负责状态变更；UI 只渲染与发事件
- 横切关注点统一：Loading/Error/Toast 等通过 BlocListener 负责副作用，避免散落 setState
