## 0.2 当前失效现象与根因分析

- 症状1：新增/删除/更新目标后，UI 与 BLoC 状态不一致，或出现重复数据/操作无效
  - 根因A：GoalPage 在 UI 层已直接调用 DatabaseHelper 完成写操作，随后又触发 BLoC 的写操作事件（如 AddGoalWithDetails/UpdateGoalWithValidation/DeleteGoalWithCleanup），造成“数据库写入执行两次”的双写。
  - 根因B：部分流程仅更新了本地状态或仅依赖 BLoC 状态，导致 currentGoal、goals、allGoals 三者不一致。
  - 根因C：操作后的统一刷新与选择（LoadGoals/RefreshGoalTree/SelectGoal）的时序/覆盖不一致。

- 症状2：日期设置后没有正确反映到 UI 或被重复写入
  - 根因：UI 直接更新 DB 后，再触发 UpdateGoalDate，导致重复更新；且未统一刷新/选择，UI 侧 currentGoal 未与 BLoC 保持一致。

- 症状3：显示选项（标题/描述/时间/倒计时）切换后不同视图/组件状态不一致
  - 根因：本地 setState 与 BLoC ToggleXXXDisplay 事件同时使用，存在状态竞争；不同渲染路径中状态来源不一致。

- 症状4：视图切换时 UI 与 BLoC viewMode 不一致或切换后内容不刷新
  - 根因：setState + ToggleViewMode 双路径下，部分渲染分支仍读取本地 currentView，部分读取 BLoC state.viewMode，导致不一致。

- 症状5：重复监听/执行副作用
  - 根因：GoalPage 存在重复的 ComponentCommunicationBloc 监听器（相同 BlocListener 注册两次），可能触发重复导航/提示等副作用。

## 0.3 修复策略总览（保持现状、止血为先）

阶段0不改变写路径的“事实归属”，以“UI→DB 的路径为主、BLoC只用于影子同步与渲染参考”为目标，严格禁止“同一业务动作在 UI 与 BLoC 同时写数据库”。具体策略：

- 写操作（增/删/改/日期/状态切换）：
  - 保留现有 UI 调 DB 的路径（短期不切到 BLoC 写入）
  - 取消随后“会触发 DB 再写入”的 BLoC 写事件（Add/Update/Delete/UpdateDate 等）
  - 改用“只读同步”事件：LoadGoals、RefreshGoalTree，必要时 SelectGoal，用于让 BLoC 状态与数据库现状保持一致
  - 增加统一的操作后刷新流程：先确保 DB 成功，再发 LoadGoals/RefreshGoalTree，必要时 SelectGoal，保证 UI（本地与 BLoC）一致

- 显示选项/视图切换：
  - 允许保留 setState 作为即时反馈（避免 UI 停顿）
  - 同时继续发送 ToggleXXXDisplay/ToggleViewMode（这类事件不写 DB，仅更新 BLoC），用于对齐 BLoC 状态与后续 BLoC 驱动渲染
  - 在渲染路径中，优先使用 BLoC 状态（阶段1会继续收敛，这里只保证不丢功能）

- 监听器与副作用：
  - 移除重复的 ComponentCommunicationBloc 监听器，避免重复副作用

- Feature Toggle：
  - 新增/使用一个“写操作通过BLoC”的开关（默认关闭），阶段0中关闭开关，阻止 UI 执行 DB 写后再发 BLoC 写事件

## 0.4 具体代码变更点（列举，暂不执行）

文件：lib/pages/goal_page.dart

一) 消除“UI写+Bloc写”双写的调用点
- 函数 _addNewGoal(Goal goal)
  - 现状：UI 调 _dbHelper.insertGoal 保存 → 之后调用 context.read<GoalBloc>().add(AddGoalWithDetails(...)) 二次写入
  - 变更：保留 UI 写；移除 AddGoalWithDetails 调用，改为：
    - context.read<GoalBloc>().add(const LoadGoals());
    - context.read<GoalBloc>().add(RefreshGoalTree());
    - context.read<GoalBloc>().add(SelectGoal(goal));
  - 预期：避免双插入；BLoC 同步数据库现状，currentGoal 指向新增目标

- 函数 _updateGoal(Goal goal)
  - 现状：UI 调 _dbHelper.updateGoal → 再发 UpdateGoalWithValidation → 双写
  - 变更：保留 UI 写；移除 UpdateGoalWithValidation 调用，改为：
    - context.read<GoalBloc>().add(const LoadGoals());
    - context.read<GoalBloc>().add(RefreshGoalTree());
    - 如当前选中目标被更新：context.read<GoalBloc>().add(SelectGoal(goal));
  - 预期：避免重复更新；状态一致

- 函数 _deleteGoal(Goal goal)
  - 现状：UI 调 _dbHelper.deleteGoal → 再发 DeleteGoalWithCleanup → 双写/异常
  - 变更：保留 UI 写；移除 DeleteGoalWithCleanup 调用，改为：
    - context.read<GoalBloc>().add(const LoadGoals());
    - context.read<GoalBloc>().add(RefreshGoalTree());
    - 重新计算并设置 currentGoal（若删除了当前目标，选择列表第一个或 null），必要时发 SelectGoal
  - 预期：删除操作稳定，状态一致

- 函数 _updateGoalDate(Goal goal, …) 或日期相关回调
  - 现状：UI 更新 DB → 再发 UpdateGoalDate → 双写
  - 变更：保留 UI 写；移除 UpdateGoalDate 调用，改为：
    - context.read<GoalBloc>().add(const LoadGoals());
    - context.read<GoalBloc>().add(RefreshGoalTree());
    - context.read<GoalBloc>().add(SelectGoal(updatedGoal));
  - 预期：日期更新后的 UI 状态稳定

二) 统一写操作后的刷新与选择
- 在上述四类函数操作成功后，标准化“刷新序列”：
  - LoadGoals() → RefreshGoalTree() → SelectGoal(必要时)
  - 说明：为减少状态“颠簸”，这三步会集中在一次 setState/Bloc 事件窗口中触发（保持当前节奏）

三) 保留显示选项/视图切换的双通路，但规范用法
- 函数 _toggleShowDescription/_toggleShowTime/_toggleCountdown/_onChangeView 等
  - 保留 setState 的即时 UI 反馈
  - 同时发 ToggleXXXDisplay/ToggleViewMode 事件，确保 BLoC 渲染路径一致
  - 检查是否存在“先由 BLoC 又 setState 反写”的循环；保留现有防抖逻辑（_lastSyncTime），必要时增加保护条件（如仅在差异时同步）

四) 移除重复 BlocListener
- 构建方法中存在两个相同的 BlocListener<ComponentCommunicationBloc, ComponentCommunicationState> 注册（重复）
  - 变更：移除重复项，保留单一监听器

五) Feature Toggle 护栏
- 使用现有 BlocFeatureToggles 或新增一个布尔开关：writeThroughBlocEnabled（默认 false）
  - 在 _addNewGoal/_updateGoal/_deleteGoal/_updateGoalDate 内，当 writeThroughBlocEnabled 为 false 时，不发送会触发 DB 写的 BLoC 事件（Add/Update/Delete/UpdateDate/…），只发送 Load/Refresh/Select 三种
  - 暂不修改 UI，先在阶段0通过开关保守运行

注：不对 GoalBloc / Repository 做任何变更；所有调整仅在 GoalPage 局部。

## 0.8 风险评估与缓解

- 风险：仅发 Load/Refresh/Select 会带来“刷新顺序/渲染时序”的瑕疵
  - 缓解：操作成功后统一顺序触发（Load → Refresh → Select），并在 UI 保持 setState 的即时反馈（阶段0允许）
- 风险：部分路径遗漏 SelectGoal 导致 currentGoal 不正确
  - 缓解：对每个写操作路径加用例覆盖；人工验证流程包含回看 currentGoal
- 风险：监听器重复导致副作用
  - 缓解：删除重复 BlocListener，转测验证
